# pypi 10Cent11@999.0.4

**Source:** pypi_malregistry · **Source label:** malicious · **Released:** not found · **Assessment:** malicious (high) · **Analysis:** ai (claude-opus-5-5)

## Summary

The sdist's setup.py overrides the setuptools `install` command with `CustomInstall`, which pip runs while building the wheel. After calling the normal install, `run` connects a TCP socket to 104[.]248[.]19[.]57:3334, duplicates it onto stdin, stdout and stderr, and spawns `/bin/sh` through `pty.spawn`, giving the remote side an interactive shell. There are no gates: the shell runs on every install that gets this far. It needs a POSIX host (top-level `import pty`), outbound reach to the C2 port, and `requests` importable in the build environment because of an unused top-level import.

## Execution

- **cmdclass** `cmdclass[install] = CustomInstall`: runs setup.py; direct_script.
- **setup_py** `python setup.py (pip install from sdist)`: runs setup.py; direct_script.

## Gates

None.

## Requirements

- network: 104[.]248[.]19[.]57:3334 (reverse shell connects out to this host:port; connect failure raises and ends the hook)
- os: linux (top-level 'import pty' needs termios (POSIX only) and the shell is /bin/sh; darwin also works, win32 fails at import)
- file_present: /bin/sh (shell spawned on the socket)
- other: python package requests importable in the build environment (unused top-level 'import requests' aborts setup.py with ImportError otherwise (pip build isolation only provides setuptools/wheel))

## Behaviour

- Ungated: reverse_shell
- Gated: none

## Notes

- The unused `import requests` means a default isolated pip build (only setuptools and wheel present) fails with ImportError before the payload, so a scanner VM should have `requests` available in the build environment (or build without isolation) to see the shell.
- Version 999.0.4 with an odd name looks like a dependency-confusion style upload; attack type is inferred from that, not from code.
- The install hangs while the shell session is open.
